# Проверка оптимизации кода Alcemy

Codex, 08.10.2026. Проверена версия с исправлениями экономики. Это аудит: рабочие симуляции, правила, цены и опубликованные документы не изменены. Прототипы запускаются отдельно.


**Внедрено:** см. [итог оптимизации и новые замеры](implementation.md). Ниже сохранён исходный аудит до внедрения.

## Коротко

- **Первый приоритет — загрузка экономики.** Модули запускают тяжёлые симуляции при загрузке; недельному плану эти готовые таблицы не нужны.
- **Поиск книги можно ускорить подготовкой текста один раз.** Прототип фильтрации быстрее примерно в 22 раза на нынешней книге; результаты поиска совпали.
- **Кеш атак ускоряет полный отчёт бестиария на 18–22% в повторных замерах.** Markdown и CSV совпали побайтово. Кеш хранит скалярные параметры, а наружу возвращает новый словарь.
- **Постоянный расчёт бонуса стоит вынести из цикла «Волшебного указания».** В трёх контрольных сценариях это сократило время на 11–26%; прибыль и состояние генератора случайных чисел совпали точно.
- **Грубое сокращение перебора кубиков требует проверки округления.** Математически равнозначный прототип меняет 53 строки CSV в восьмом знаке и итоговый Markdown. Для первого прохода рекомендуем прежний алгоритм с кешем.

Как читать: ниже — рекомендации Codex в порядке внедрения, затем измерения и команды воспроизведения. Данные каждого прототипа сохранены в [results.json](results.json).

В weekly_economy_report.py уже есть повторное использование дохода для одного мастерства. Там полезно заменить подмену globals явным аргументом или контекстом расчёта. Глобальный lru_cache для случайной volume_stats сейчас ставить нельзя: вызов потребляет RNG, и кеш меняет последующие выборки. Сначала нужен отдельный Random и явные параметры прогона.

Объёмная варка при загрузке sim_volume.py рассчитывает 12 сценариев по 20 000 изделий. В report.py этот модуль исполняется через несколько путей: напрямую и через sim_player.py и sim_week.py. Недельная сборка сначала получает готовые таблицы, затем выполняет собственные расчёты. Профиль недельной сборки: 12,83 из 14,31 секунды внутри runpy.run_path; непосредственная построенная таблица занимает оставшуюся часть. Это измерение с накладными расходами профилировщика, а не обещание ускорения в десять раз.

В симуляции «Волшебного указания» катализатор переносится между днями, а единицы чародейства восстанавливаются на границе дня. При распараллеливании независимых кусков нельзя молча сбрасывать катализатор на каждой границе. Число дней и правила остановки сохраняются. Уменьшение выборки лишь ради скорости ухудшит точность отчёта.

## Измерения сборки

Время одного запуска на этой облачной машине. Профиль и обычный запуск измерены отдельно; они не дают гарантии времени на другом компьютере. Генерация выполнена в свежей временной копии без .git.

В профиле report.py функция sim из sim_guidance.py занимает 37,67 из 54,25 секунды, около 69%. Вызовов — 36, каждый по 100 000 дней. Здесь находятся главные затраты расчёта, а не в точной формуле прибыли. Динамический exec осложняет профиль: разные функции получают одинаковое имя файла <string>. Для дальнейшей работы стоит компилировать с реальным именем файла или перейти на импорты.

### Прототипы и границы измерений

- **Поиск:** 47 глав и документов, 845 379 символов. Шесть запросов по 100 повторов, медиана семи серий: 3896,8 мс → 177,8 мс. Измерена фильтрация, без построения DOM результатов и прокрутки. Поэтому ускорение в 22 раза относится к фильтру, а не ко всему интерфейсу. Во всех шести запросах совпали списки и порядок результатов.
- **Постоянный бонус:** три сценария по 20 000 дней, медиана трёх серий. 81,27 → 64,34 мс; 81,32 → 60,16 мс; 54,86 → 48,62 мс. В каждом из девяти парных прогонов прибыль и состояние RNG совпали точно. Это измерения функции, а не всей сборки экономики.
- **Кеш атак:** полный calculate + render, медиана трёх сборок: 2,537 → 1,995 секунды. В каждой серии кеш сначала пуст; после сборки — 105 021 попадание и 217 записей. Markdown и CSV идентичны опубликованным. Два повтора тем же скриптом подтвердили ускорение на 18–22%; их измерения также сохранены в results.json.
- **20 исходов вместо 400:** проверены 6760 сочетаний КД, бонуса, преимущества/помехи и автоматического крита. Максимальное различие вероятностей — 1,04 × 10⁻¹⁴. Изолированная функция быстрее примерно в 25 раз, но полный отчёт изменяется: 53 строки CSV, например 14.15764062 → 14.15764063. В текущую реализацию этот прототип не перенесён.

У книги и карточек сборка уже занимает доли секунды. Проверка ссылок книги использует список ids; замена на множество полезна по сложности, но сейчас это низкий приоритет. Распределения кубиков и вероятности спасбросков бестиария уже имеют кеши; добавлять ещё один общий кеш без профиля не требуется. Новый слой зависимостей, NumPy и многопроцессность для первого прохода не нужны.

## Проверки и воспроизведение

Пройдены 76 Python-тестов, проверка карточек, браузерный тест книги и тест помощника: наличие материалов, нехватка, общие формулы, испорченные запасы, чистота, прогресс 5.5, экспорт, восстановление и сохранение. Проверочная сборка не меняла рабочие игровые документы.

Из корня Alcemy:

```sh
python3 -B scripts/optimization_audit/benchmark_python.py
python3 -B scripts/optimization_audit/benchmark_report.py
node scripts/optimization_audit/benchmark_search.cjs
python3 -B -m unittest discover -s scripts -p 'test_*.py' -q
```

Прототипы пишут новые JSON только в /tmp. Для браузера нужны те же Playwright и Chromium, что для test_player_book.cjs; путь можно задать PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH. benchmark_python.py использует изолированный AST-загрузчик экономических тестов, чтобы не запускать побочные сборки. benchmark_report.py проверяет весь отчёт; расхождение варианта weighted записывает как результат, а current и cached обязаны совпасть.

Для повторного cProfile запустить команды из таблицы в новой временной копии, например python3 -B -m cProfile -o /tmp/economy.prof scripts/report.py. Профиль добавляет заметные накладные расходы; не сравнивать его время с обычным запуском.
