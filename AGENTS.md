# Ведение проекта Codex

С 01.11.2026 проект ведёт Codex: пользователь поручил вести здесь документы кампании, ремёсла, код, сборку и общую ветку. Это постоянный порядок работы; отдельного подтверждения на интеграцию проверенных изменений своей задачи не требуется.

## Сначала выбрать кампанию

В репозитории ведутся две самостоятельные кампании: **Талис** и **Шаэрра**. Игрок подтвердил, что это разные кампании. Указатель — [Кампании.md](Кампании.md).

- Для Талиса читать [состояние Талиса](Состояние%20проекта.md) и `CLAUDE.md` (предметная памятка Талиса, имя сохранено для совместимости).
- Для Шаэрры читать `Шаэрра/AGENTS.md`, `Шаэрра/Состояние кампании.md` и `Шаэрра/README.md`. Её материалы, состояние и дальнейшие записи хранить внутри `Шаэрра/`.
- Правила, решения мастера, события, союзников, ресурсы и планы одной кампании не переносить в другую без явного указания игрока. Предметные разделы ниже о листе Талиса, алхимии, LSS, его журнале и сохранениях относятся к Талису.

Общий порядок веток, сохранности исходников и проверки изменений действует для обеих кампаний. Для текстов читать `WRITING_QUICK.md`, для редакторских задач — также `WRITING.md`; предметные примеры и глоссарий Талиса не задают правила другой кампании. Явные указания пользователя имеют приоритет.

## Рабочая ветка и завершение задачи

- Основная ветка: `claude/alchemy-talis-crash-test-6g8sk7`. Её имя историческое; переименование не требуется. Codex ведёт её сам.
- Перед новой задачей проверить `git status --short`, выполнить `git fetch origin` и создать `codex/<задача>` от актуальной основной ветки. Незавершённую работу сохранять; ветку поверх чужих или невыясненных изменений не переключать.
- По окончании проверить diff, выполнить проверки по области изменения, закоммитить явный список файлов и отправить рабочую ветку обычным push. PR создавать только по просьбе.
- Затем обновить основную ветку и объединить готовую задачу через `git merge --no-ff`. При новых пересекающихся изменениях разобраться в них и повторить затронутые проверки; результаты генерации пересобирать из объединённых исходников. Если итоговое дерево совпадает с уже проверенным, повторный полный прогон не нужен.
- Отправить основную ветку обычным push и сверить удалённый SHA. Задача завершена, когда проверенные исходники и нужные готовые документы находятся в основной ветке. Если пользователь просит оставить работу отдельно, следовать его указанию.
- Не выполнять force push, удаление чужих веток или reset с потерей изменений. Дополнительный worktree создавать только по просьбе пользователя. Второго агента в том же checkout не запускать.
- В ответе кратко назвать результат, проверки, необходимость импорта/замены HTML и основную ветку с полным SHA. Не выдавать подготовленный файл за изменение сохранения в браузере или опубликованной страницы.

## Где находится актуальное состояние

- `Состояние проекта.md` — точка входа для следующего запуска: текущее положение кампании, подтверждённый снимок, порядок обновления и ограничения доступа. Обновлять при изменении этих сведений.
- Правила и статусы решений — в полном тексте правил, очереди и журнале решений. Карта файлов и предметные ограничения — в `CLAUDE.md`.
- События и броски — в логах сессий в `Источники/`. Дополнения встраивать в соответствующую сцену с сохранением реплик, чувств и оговорок игрока.
- Постоянные параметры и имущество — в `Талис — лист персонажа.md`. Текущие сумки, материалы и монеты задаёт снимок по указателю `Источники/Сохранения/current.json`; блоки `current-*` в листе и начальные запасы помощника собираются из него. Эти блоки и дубли запасов в Python вручную не вести. Новые операции записывать с причиной и итогом; не учитывать одну продажу, награду или трату дважды.
- JSON в `Источники/Сохранения/` — датированные выгрузки помощника. Новый снимок сохранять отдельным файлом с датой и при необходимости временем; старые не заменять без причины. Подтверждённые игроком действия после выгрузки учитывать поверх неё: подготовить новый снимок, переключить `current.json`, выполнить `check_all.py --scope inventory --build`. Датированный исходный снимок не переписывать. При противоречии уточнять конкретную операцию, а не сбрасывать состояние по старому листу.
- Рабочее сохранение помощника, начальные данные HTML и опубликованная страница независимы. Замена HTML не переносит текущие остатки; JSON не заменяет подписи интерфейса. Для переноса выдавать JSON, для изменения интерфейса — HTML, при необходимости оба файла.
- Сохранять снимки только с игровыми данными. Учетные данные и личные идентификаторы игрока в репозиторий не записывать. Файлы для передачи игроку выдавать доступными ссылками; временная папка среды не заменяет репозиторий.

## Ремёсла во время сессии

- В начале сверить время, деньги, материалы, прогресс и доступные ресурсы с последним подтверждённым сохранением и последующими сообщениями игрока.
- Для подхода записывать проект, место, исходные броски, бонусы, помеху/преимущество, переброс и расход способности, итог, прогресс, материалы, деньги и время. Неизвестные условия не додумывать.
- После каждого подхода сообщать итог и остатки. Отменённые пробы и ручные поправки не должны оставлять ложные часы или расходы по дням.
- После законченного блока или сессии сохранить журнал и лист, подготовить новый JSON по подтверждённым данным. Проверить его штатным валидатором и импортом в отдельном браузерном контексте, сохранив исходный снимок.
- Описания проектов не заменяют действующие правила. Бонусы и последствия сверять с актуальным листом и принятыми решениями.

## Предметные ограничения

- Не менять цены, механику, округление, баланс и решения мастера без соответствующего решения игрока. Различать факт, предложение Codex и утверждённое правило.
- Не приписывать игроку предложенный порядок исследований. Порядок выбирает игрок.
- Соблюдать разделение знаний игрока, персонажа и мастера из `CLAUDE.md`. В материалы мастеру не переносить сведения только для игрока.
- Ник игрока в Telegram никогда не записывать в файлы.

## Генерация и проверки

- Менять исходник или шаблон; собранные HTML, карточки, таблицы и отчёты вручную не редактировать.
- Генерировать в свежей временной копии вне checkout, без `.git`. Python запускать с `-B`. Переносить только относящиеся к задаче результаты; не удалять заранее существовавшие пользовательские файлы.
- Выбирать минимальные проверки по затронутой области. Дополнение лога, записки или реплики: вручную сверить изменённую сцену с сообщением игрока, выполнить `python3 -B scripts/check_all.py --quick --build --files "Путь к логу.md"`. Для источников библиотеки автоматически выбирается `library`: сборка и проверка её актуальности, без тестов интерфейса, буфера обмена, мобильной вёрстки и экономики. Новых тестов для простой правки текста не писать.
- Для сборки запасов — `--scope inventory --build`, интерфейса помощника — `--scope helper --build`, пульта — `--scope master --build`; для обычного документа с HTML — `--scope text --files "Документ.md" --build`. Код и шаблоны проверять относящимися к ним тестами. Для алгоритма выбора проверок — `--scope checks` и проверка реального маршрута сборки в отдельной копии; неизменённый интерфейс из-за этого не прогонять. Неизвестный общий код, общие правила и крупный выпуск требуют полного `--browser`; `--slow` добавлять при изменении расчётов экономики. Путь Chromium — `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`.
- До запуска при сомнении посмотреть `--quick --plan --files ...`: это только план, не проверка. Пустой план отмечается как пропуск с кодом 2, а не успешный прогон. Если для текста нет автоматической проверки, выполнить ручную сверку и явно назвать её. CI выбирает область по фактическому diff, в том числе после слияния в основную ветку; полный прогон вручную остаётся доступен. Подробности — `scripts/README.md`.
- Не добавлять тесты, дублирующие простую правку текста. При изменении поведения выбирать проверки, которые воспроизводят проблему. После успешных проверок не запускать их повторно без новой причины.
- `STATUS.md` и `questions.csv` генерируются из вопросов и решений; для заметок о сопровождении использовать `Состояние проекта.md`.
- Публикация на внешнем сервисе — отдельное действие. Проверять наличие инструмента и доступа; при их отсутствии выдавать проверенные файлы и прямо указывать, что опубликованная версия не изменена.
